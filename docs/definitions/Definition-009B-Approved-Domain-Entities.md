# Definition-009B
## Approved Domain Entity Specification
### Sprint 1 Issue #9

**Status:** Approved domain specification for the Issue #9 minimum model
**Date:** 2026-11-01
**Scope:** Domain identity, names, relationships, and validation for Artist,
Collection, Model, and Tag
**Excludes:** Persistence schema, repository operations, migrations, import
semantics, and implementation

## 1. Purpose and Authority

This specification resolves the minimum entity decisions left open by
[Definition-009A](Definition-009A-Domain-Entity-Foundation.md) for the four
Domain entities required by [Issue #9](https://github.com/mike-n-va/3d-print-vault/issues/9).
It provides domain-level detail for a future, separately authorized
implementation. It does not implement entities or authorize database,
repository, or import behavior.

The specification applies within the approved project boundaries:

- `DPV.Domain` owns these entities and their domain validation.
- `DPV.Domain` remains free of framework, UI, persistence, filesystem, and
  dependency-injection dependencies.
- `DPV.Infrastructure` may later translate the domain model to storage;
  that translation is not specified here.
- This document does not add a project, layer, or Sprint feature.

The domain entity decisions below resolve the relevant Issue #9 modeling
unknowns in `DPV-DATA-001`. File identity, filesystem locations, import and
rescan behavior, storage schema, migration strategy, and repository operations
remain governed by their existing decisions and are not resolved here.

## 2. Shared Entity Rules

### Identity

Every entity has an immutable `Guid Id`.

- A new ID is generated by the Domain entity creation path using
  `Guid.NewGuid`, independent of any database or repository.
- `Guid.Empty` is invalid.
- The ID remains stable for the lifetime of that entity.
- Entity identity and equality are determined by `Id`, not object reference or
  `Name`.
- Names are not identity and are not unique keys.
- No composite, integer, or string identity is used for these entities.

### Name

Every entity has a required `Name` value.

- A name must be non-null, non-empty, and contain at least one non-whitespace
  character.
- Leading and trailing whitespace is removed when accepting a name.
- The resulting value is retained as entered; no case folding, Unicode
  normalization, slugging, or other canonicalization is performed.
- No maximum length or uniqueness rule is imposed by this minimum domain
  specification.

Names may therefore repeat across entities of the same type. Any future
search, display, or duplicate-management behavior must not silently change
these identity or validation rules.

`Name` may change after creation, but every accepted value must satisfy the
same trimming and non-whitespace validation rules. This specification does
not prescribe a public mutation API or repository update operation.

### Optional Properties

No additional optional scalar properties are approved for the Issue #9
minimum. In particular, descriptions, URLs, aliases, audit timestamps,
lifecycle flags, and file metadata are excluded until separately specified.

Relationships identified below are the only optional entity data in scope.

## 3. Entity Specifications

### Artist

**Purpose:** Represents a creator.

| Property | Requirement |
|---|---|
| `Id` | Required immutable `Guid`; must not be `Guid.Empty`. |
| `Name` | Required validated name under §2. |
| Other scalar properties | None in the minimum model. |

**Validation:** Apply the shared identity and name rules. Do not enforce
name uniqueness.

**Ownership boundary:** `DPV.Domain` owns the concept and validation.
Artist contains no database, UI, or filesystem behavior.

**Relationships and cardinality:**

- An Artist may be associated with zero or more Collections.
- A Collection may be associated with zero or one Artist.
- No direct Artist–Model relationship is defined.
- An Artist has no required child collection or navigation property; the
  relationship's inverse can be obtained by a future consumer without
  changing the entity contract.

The optional Collection association permits a collection whose creator is
unknown without inferring one from a directory or file name.

### Collection

**Purpose:** Represents a release or pack.

| Property | Requirement |
|---|---|
| `Id` | Required immutable `Guid`; must not be `Guid.Empty`. |
| `Name` | Required validated name under §2. |
| `Artist` | Optional association to zero or one Artist. |
| Other scalar properties | None in the minimum model. |

**Validation:** Apply the shared identity and name rules. Do not enforce
name uniqueness.

**Ownership boundary:** `DPV.Domain` owns the concept and association
semantics. No persistence or presentation types are exposed.

**Relationships and cardinality:**

- A Collection is associated with zero or one Artist.
- An Artist may have zero or more Collections.
- A Collection may contain zero or more Models.
- A Model may be associated with zero or one Collection.
- No Collection–Tag relationship is defined.

The Collection–Model relationship does not require either side to have an
associated counterpart. Artist and Collection associations must never be
inferred from paths or folder names by this entity specification.

### Model

**Purpose:** Represents one logical printable asset in the catalog. It is
not the STL file, physical file location, or file content itself.

| Property | Requirement |
|---|---|
| `Id` | Required immutable `Guid`; must not be `Guid.Empty`. |
| `Name` | Required validated name under §2. |
| `Collection` | Optional association to zero or one Collection. |
| `Tags` | Zero or more distinct Tag associations; no duplicate Tag identity
  within one Model. |
| Other scalar properties | None in the minimum model. |

**Validation:** Apply the shared identity and name rules. Reject a null tag
association collection; the association collection is non-null and empty
when no Tags are associated. Reject null entries or repeated Tag IDs when
associations are supplied. Do not enforce name uniqueness.

**Ownership boundary:** `DPV.Domain` owns the logical catalog concept and its
association invariants. Files, paths, hashes, filesystem access, and
persistence representations are outside this entity.

**Relationships and cardinality:**

- A Model may belong to zero or one Collection; a Collection may contain
  zero or more Models.
- A Model may have zero or more Tags; a Tag may be associated with zero or
  more Models.
- No direct Artist–Model relationship is defined. The conceptual hierarchy
  is through Collection when that association exists.

The one-Model-per-logical-printable-asset definition does not decide how an
imported STL or any other file maps to a Model. One or more source files may
be associated with a logical asset only under a separately approved
file/asset contract. No file path or file bytes are an entity property here.

### Tag

**Purpose:** Represents a named classification label applied to Models.

| Property | Requirement |
|---|---|
| `Id` | Required immutable `Guid`; must not be `Guid.Empty`. |
| `Name` | Required validated name under §2. |
| Other scalar properties | None in the minimum model. |

**Validation:** Apply the shared identity and name rules. Do not enforce
name uniqueness.

**Ownership boundary:** `DPV.Domain` owns the classification concept and
name validation. Tag does not depend on search, UI, or persistence
implementation.

**Relationships and cardinality:**

- A Tag may be associated with zero or more Models.
- A Model may be associated with zero or more Tags.
- Tag does not classify Artist or Collection in this minimum specification.
- No tag hierarchy, parent/child relationship, or automatic tagging is
  defined.

## 4. Relationship Summary

| Relationship | Cardinality | Domain rule |
|---|---|---|
| Artist–Collection | Artist `0..*` Collections; Collection `0..1` Artist | Collection may have an unknown/unassigned Artist. |
| Collection–Model | Collection `0..*` Models; Model `0..1` Collection | A Model can exist in the catalog without a Collection. |
| Model–Tag | Model `0..*` Tags; Tag `0..*` Models | Associations are distinct by Tag identity for each Model. |
| Artist–Model | None | No direct association; do not infer one. |
| Artist–Tag | None | Not part of the minimum model. |
| Collection–Tag | None | Not part of the minimum model. |

These are domain association semantics only. This table does not prescribe
foreign keys, join tables, navigation-property implementation, cascade
behavior, or database cardinality enforcement.

## 5. Explicitly Out of Scope

This specification does not define:

- Database tables, columns, foreign keys, indexes, or constraints.
- Repository interfaces or operations such as Create, Update, Delete,
  GetById, Search, or List.
- Schema versions, migrations, transactions, or Dapper mappings.
- File-location or source-root entities, path normalization, or file hashes.
- Import, scanning, rescan, relocation, duplicate, or missing-file behavior.
- Deletion, archival, audit timestamps, lifecycle state, or merge behavior.
- UI display formatting, search matching, or tag assignment workflows.

The existing storage and import questions in `DPV-DATA-001` remain open.
Nothing in this document authorizes the entity model to store model file
bytes or assume that a filesystem path is a Model identity.

## 6. Issue #9 Implementation Readiness

This specification provides the Issue #9 minimum entity shape and validation
rules without introducing persistence or UI dependencies. A separate
implementation authorization may now create the four Domain entities and
focused tests against these requirements.

Issue #9 is not marked complete by this definition document alone. Its
positive acceptance criteria require the source declarations to exist, and
the no-persistence and no-UI-dependency criteria require verification after
implementation.
